### 1-2. 画面側のタイマー・閾値

| 項目 | 値 | 備考 |
| :--- | :--- | :--- |
| 取得タイムアウト | 15秒 | `?mode=summary` のみ 12秒 |
| 手動更新のクールダウン | 5秒 | 推しスケ！の再読込、推しマド！の「最新取得」 |
| 自動取得の最小試行間隔 | 15秒 | 推しマド！（`MIN_AUTO_FETCH_GAP_MS`） |
| 鮮度低下の警告 | 30分 | データが更新されていない時間 |

| 「まもなく配信開始」 | 開始まで30分以内 | |
| タグの自動折りたたみ | 該当件数が **4件未満** | 推しスケ！（`computeLocalFolded`）、GAS（`TAG_AUTO_VISIBLE_MIN_COUNT`）とも 4。ブックマークレットは GAS が返す `isFolded` を使用 |

**タグの折りたたみの適用範囲**

- タグマスタの表示設定が優先されます：`always` は常に展開、`fold` は常に折りたたみ、空欄・その他は自動判定です。
- 推しスケ！の配信スケジュール画面は、メイン・サブとも全件展開です。
- チャンネル一覧は、メインタグ未選択のときのみ、メイン・サブとも閾値で折りたたみます。メインタグ選択中は、絞り込まれたサブタグを全件展開します。
- 推しマド！のドロワーは、メインタグを全件表示し、折りたたみはありません。

## 2. バックエンド（GAS）

### 2-1. 更新処理 `updateLiveCache`（15分おき）

1. `LockService` で5秒待つ。取得できなければスキップする。
2. `配信監視一覧` から、チャンネル ID・タグ・表示名を読む。
3. `メン限手動枠` と、前回のキャッシュを読み込む。
4. 監視チャンネルごとに、アップロード一覧を `PlaylistItems.list`（10件）で**直列**に取得する。
5. 動画 ID をまとめ、`Videos.list` を50件ずつ取得する。
6. 前回のデータとマージする（未検出カウント、API 失敗時の保持）。
7. `配信キャッシュ` シートへ書き込み、`CacheService` に分割保存する。

### 2-2. 更新処理 `updateChannelDirectory`（1日1回）

ディレクトリの全チャンネルを `Channels.list`（50件ずつ）で更新し、チャンネルごとの最新動画を `PlaylistItems.list`（1件）で**直列**に取得します。

### 2-3. API 仕様（`doGet` / `doPost`）

| メソッド / パラメータ | 呼び出し元 | 返却内容 |
| :--- | :--- | :--- |
| `GET ?mode=summary` | `index.html`（タイムアウト 12秒） | `liveCount`、`upcomingCount`、`channelCount`、`lastUpdated`、`lastUpdatedMs`、`lastAttemptedMs`、`updateStatus`、`errorSummary` |
| `GET ?mode=schedule` | `oshisuke.html`（初期表示） | `lives`、更新情報（上記と同じ）、`tagOrder`、`tagMeta`、`channelCount` |
| `GET ?mode=lives` | `oshimado.html` | `lives`、更新情報、`tagOrder`、`tagMeta` |
| `GET ?mode=tags` | ブックマークレット（チャンネルページ） | `channels` を `{ channelId, channelUrl, tags }` に軽量化したものと、`tagOrder`、`tagMeta` |
| `GET`（パラメータなし） | `oshisuke.html`（チャンネル一覧タブ） | 全件（`lives`、`channels`、更新情報、`tagOrder`、`tagMeta`） |
| `GET ?action=addMember` / `addChannel` | （旧形式のリクエスト） | 拒否し、POST が必須であることを示すエラー JSON を返す |
| `POST` `action: 'addMember'` | ブックマークレット（動画ページ） | `token` を検証し、`Videos.list` で状態を確認。終了した枠は削除。一般枠は `メン限手動枠` から除外してキャッシュに反映。メン限枠は `メン限手動枠` に保存してキャッシュに反映 |
| `POST` `action: 'addChannel'` | ブックマークレット（チャンネルページ） | `token` を検証し、`Channels.list` とアップロード一覧から情報を取得。`チャンネルディレクトリ` へ追記・更新し、`タグマスタ` に反映して `CacheService` を再構築 |

- `mode` の `summary`・`schedule`・`lives` は、チャンネル配列の結合を省略して応答します。
- `POST` は `Content-Type: text/plain;charset=utf-8` の JSON ボディで送ります（CORS のプリフライトを発生させず、トークンを URL に載せないため）。
- `doGet` は認証なしで応答します。

### 2-4. データストレージとキャッシュ（3層）

| 層 | 対象 | 構造・制御 |
| :--- | :--- | :--- |
| 第1層：ブラウザ `localStorage` | `LIVES` / `FULL`（GitHub Pages） | `LIVES` は `channels` を除外して保存。`FULL` は既存の `channels` を壊さず、配信枠とメタ情報だけを非破壊でマージ |
| 第1層：ブラウザ `localStorage` | `BM_TAGS`（`www.youtube.com`） | `?mode=tags` の応答をそのまま保存。`addChannel` が成功したら破棄 |
| 第2層：GAS `CacheService` | 本体 `LIVE_SCHEDULE_JSON_V8`、分割 `LIVE_SCHEDULE_JSON_V8_CH_<genId>_<idx>` | TTL は 21600秒（6時間）。`channels` 配列を約80KB（`81920` bytes）単位で、世代 ID 付きのチャンクに分割。新しい世代を先に書き、成功後に旧世代を削除。保存失敗や欠損を検知したら全キーを削除し、スプレッドシートから再構築する |
| 第3層：スプレッドシート | 5シート（下記） | `LockService` の排他制御下で、`writeRowsSafely_` によりテキスト書式（`@`）を設定して一括書込 |

`CacheService` の1キーは100KB（102,400 bytes）が上限です。

**シート構成**

| シート | 列数 | 役割 |
| :--- | :--- | :--- |
| `配信監視一覧` | — | 監視対象のマスター（A列＝チャンネル ID、B列＝タグ、C列＝表示名）。GAS は読み取りのみ。並び順が、チャンネル別表示の順になる |
| `配信キャッシュ` | 14 | 配信中・配信予定のキャッシュ |
| `メン限手動枠` | 8 | ブックマークレットで登録したメン限枠。定期更新による上書きから保護 |
| `チャンネルディレクトリ` | 9 | チャンネル一覧ビュー用のデータ |
| `タグマスタ` | 3 | タグの区分（メイン／サブ）と表示設定（常時／折りたたみ／自動） |

### 2-5. トリガー

トリガーはコード内で作成しません。Apps Script の画面から、手動で設定します。

| 関数 | 種類 | 間隔 |
| :--- | :--- | :--- |
| `updateLiveCache` | 時間主導型・分ベース | 15分おき |
| `updateChannelDirectory` | 時間主導型・日付ベース | 1日1回 |

## 3. フロントエンド仕様

### 3-1. ポータル（`index.html`）

`FULL` と `LIVES` のうち、`savedAtMs` が新しいキャッシュで先に描画します。そのあと `?mode=summary` を非同期で取得し、ステータスストリップ（配信中・予定・チャンネル数・更新日時・警告）を更新します。警告は、更新状態が `failed` または `partial` のときのみ表示します。

### 3-2. 推しスケ！（`oshisuke.html`）

- 2つのビュー（配信スケジュール、チャンネル一覧 `#channels`）を切り替えます。初期表示は `?mode=schedule` で行い、チャンネル一覧タブへ切り替えたときにフルデータを取得します（通信中に切り替えた場合は、通信の完了後に全件を取得します）。
- 2階層タグ（メイン／サブ）を、表示中のデータから動的に抽出します。折りたたみは 1-2 のとおりです。
- 再読込のクールダウンは 5秒です。通信失敗・取得エラー・鮮度低下（30分）・更新停止の疑い（45分）を、警告バッジで示します。
- 画像の読み込みエラーは、イベント委譲で集中的に処理します（インラインの `onerror` は使いません）。

### 3-3. 推しマド！（`oshimado.html`）

**レイアウト**

| 識別子 | 窓数 | 備考 |
| :--- | :--- | :--- |
| `1x2` | 2 | |
| `2chat` | 2 | 下段にチャットを並べる。下段の高さは `minmax(min(425px, 54%), 1.1fr)` を確保 |
| `2x2` | 4 | |
| `1plus3` | 4 | メイン枠＋サブ3枠。メイン枠の番号は `main` パラメータで保持（既定は 1） |
| `3x2` | 6 | 最大 |

- 窓の DOM は破棄せず、CSS Grid の配置だけを切り替えます。
- セットされた枠の数がレイアウトの窓数を超えると、自動で切り替えます（2枠以下は `2chat`、4枠以下は `2x2`、それ以上は `3x2`）。

**非表示枠と音声**

- 窓数の少ないレイアウトへ切り替えたとき、隠れた枠は元のミュート状態を退避したうえで、一時停止してミュートします。
- ソロ音声の枠が隠れたときは、表示中の枠（メイン枠を優先）へ移譲します。このとき、隠れた枠の退避値は「ミュート」に固定されるため、復帰時に2枠が同時に鳴ることはありません。
- 隠れた枠が再び表示されたときは、退避した状態に戻して再生します。
- 最初にセットした枠は音声ON（ソロ）、2枠目以降はミュートでセットします。URL から復元するときは、全枠ミュートで始めます。

**チャット**

- `2chat`：1・2窓目のチャット（`live_chat?v=...&embed_domain=...&dark_theme=1`）を下段に並べます。
- その他：右サイドバーに、窓ごとのタブで表示します。
- 表示しないチャットの `iframe` は破棄します。

**ショートカット**：`1`〜`6`（ソロ）、`M`、`U`、`C`、`D`、`F`、`Esc`（ドロワーを閉じる）。入力欄へのフォーカス中、および `Ctrl` / `Alt` / `Meta` との同時押しでは無効です。

**ドロワー**

- 配信中・予定の一覧は `?mode=lives` のデータを使います。カードのクリックで、最初の空き枠へセットし、セット済みのカードのクリックで解除します。
- メインタグでの絞り込みと「LIVE のみ」があります。
- 「配信中を一括展開」は、既存の枠をクリアし、配信中の枠を最大6件セットします。
- 手動追加は、URL・動画 ID を、カンマ・スペース・読点・改行で区切って入力します。「空き枠へ追加」は重複を除いて追加し、「入力枠で一括セット」は全枠を置き換えます。
- 対応する形式：11桁の ID、`watch?v=`、`youtu.be/`、`/live/`、`/shorts/`、`/embed/`。

**URL の同期**：`?v=ID1,-,ID3&layout=<識別子>&main=<1〜6>`。空き枠は `-` で保持します。

**自動更新**：`?mode=lives` を3分ごとに取得します。タブが非表示の間は取得せず、表示に戻ったとき、最後の成功から3分以上、かつ最後の試行から15秒以上たっていれば取得します。取得結果は、`LIVES` と（存在する場合）`FULL` に、非破壊でマージします。

**その他**：ページには `noindex, nofollow` の meta を設定しています。

## 4. Chrome 拡張機能の連携プロトコル

### 4-1. 構成

| 項目 | 値 |
| :--- | :--- |
| 名称・バージョン | `oshimado-ss` v1.3.3（Manifest V3、最小 Chrome 102） |
| 権限 | `storage` のみ（ホスト権限なし） |
| コンテンツスクリプト | ① `youtube.com/embed/*`、`youtube-nocookie.com/embed/*`、`youtube.com/watch*`（全フレーム、`document_start`）<br>② 推しマド！のページ（トップフレームのみ、`document_idle`） |
| サービスワーカー | `background.js` |

### 4-2. メッセージ

| 機能 | 経路 | メッセージ | 検証 |
| :--- | :--- | :--- | :--- |
| 起動の確認 | `oshimado.html` ↔ `content.js` | `OSHIMADO_EXT_PING` → `OSHIMADO_EXT_READY`（`version: '1.3.3'`） | `event.source === window` かつ `event.origin` が推しマド！のオリジン |
| ミニウィンドウ | `oshimado.html` → `content.js` → `background.js` | `OSHIMADO_OPEN_WATCH_POPUP_REQ` → `chrome.runtime.sendMessage('OSHIMADO_OPEN_WATCH_POPUP')` → `OSHIMADO_OPEN_WATCH_POPUP_RES` | `background.js` が、送信元の `origin` と `url` の先頭一致、および `WATCH_URL_RE` を検証 |
| スクリーンショット | `oshimado.html` ↔ `content.js`（埋め込みフレーム） | `OSHIMADO_CAPTURE_REQUEST` → `OSHIMADO_CAPTURE_RESULT` | 送る側は、応答が対象 `iframe` の `contentWindow` から来たことを検証。受ける側は `event.source === window.parent` かつオリジン一致 |

- 起動の確認：拡張機能が応答しなければ、待たずに `window.open` へフォールバックします。
- ミニウィンドウの要求：応答待ちは3秒です。超過した場合や、拡張機能が未検出の場合は、`window.open` へフォールバックします。
- スクリーンショットの要求：応答待ちは2秒です。

### 4-3. ミニウィンドウ

- 開く URL：`https://www.youtube.com/watch?v=<11桁>#oshimado_popup`（この形式のみ許可）。
- 大きさ・位置（要求値を次の範囲に丸める）：幅 320〜1920（既定 640）、高さ 360〜1440（既定 780）、`left` 0〜7680、`top` 0〜4320。
- 要求は `popupQueue` で直列に処理します。連続して要求しても、2回目以降は1回目の窓を再利用します。
- 窓 ID とタブ ID は、メモリと `chrome.storage.session`（`popupWindowId` / `popupTabId`）に保持し、サービスワーカーが再起動しても同じ窓を再利用します。窓が閉じられると、保持した値を消去します。
- 再利用時は、同じタブの URL を更新して最前面にします。
- ミニウィンドウ内の自動制御（`content.js`）は、URL ハッシュ `#oshimado_popup`、または `sessionStorage` のフラグがあるタブでのみ動作します。フラグは、そのタブの中で別の動画に移動しても維持されます。通常のタブには干渉しません。
  - 動画の一時停止：開始から6秒間。プレイヤー内のクリック、または `Space` / `K` で解除。
  - ライブチャットの自動折りたたみ：最大30秒間、状態を監視して確定。
  - 動画 ID が変わるたびに、これらをやり直す。

### 4-4. スクリーンショット

- `<video>` の `videoWidth` × `videoHeight` を `<canvas>` に描画して PNG にします。解像度は、再生中の映像の実際の解像度です。
- ファイル名：`推しマド_#<枠番号>_<ラベル>_<YYYYMMDD_HHMMSS>.png`。ラベルは、チャンネル名、なければタイトル、さらになければ動画 ID。使えない文字は `_` に置換し、全体が80文字程度に収まるようにラベルを切り詰める（ラベルは最低8文字）。

### 4-5. 埋め込み待機画面の補正

`window.top !== window.self` かつ `location.ancestorOrigins[0]` が推しマド！のオリジンの埋め込みフレームに、`style#oshimado-embed-ui-fix` を注入します。待機サムネイルを `background-size: contain` にし、「通知を受け取る」バーを横並び、幅 520px 以下ではコンパクト表示にします。ライブチャットの `iframe` は対象外です。

### 4-6. 制約

- ミニウィンドウの `left` は 0 以上に丸められるため、プライマリより左や上のモニターにいる場合は、位置が 0 に寄ります。
- 待機画面の補正とチャットの自動折りたたみは、YouTube 側のクラス名や要素名に依存します。チャットを閉じるボタンの代替セレクタは、日本語の `aria-label` を前提としています。

## 5. ブックマークレット仕様

| 項目 | 内容 |
| :--- | :--- |
| 設定 | `CFG.GAS_URL`、`CFG.TOKEN`、`CFG.BM_CACHE_KEY` をインラインで保持（外部ファイルを読み込めないため）。`TOKEN` が未設定（「トークン」を含む）ならアラートを出して中断 |
| 対象ページ | 動画：`?v=<11桁>` または `/live/<11桁>`（`/shorts/` は非対応）。チャンネル：`/channel/UC<22桁>`、`/@ハンドル`（2〜30文字）。チャンネル ID は、取れなければ canonical リンクと meta から補う |
| 動画の登録 | `ytInitialPlayerResponse` から情報を抽出（取れなければ、ページ内の `<script>` から探す）。枠種（一般／メン限）を選び、`POST addMember` |
| 送信項目（`addMember`） | `token`、`videoId`、`channelId`、`channelTitle`、`title`、`thumbnail`、`status`、`startTimeMs`、`isMember`（`'0'` / `'1'`） |
| 状態の判定 | `isLive` または `isLiveNow` なら `live`、それ以外は `upcoming`。開始時刻は、実開始、予定開始、公開日の順で、取れなければ現在時刻（最終的な状態は GAS が API で確認する） |
| チャンネルの登録 | タグを、キャッシュ（`BM_TAGS`）から先に表示し、`?mode=tags` で最新化。登録済みのチャンネルは、`channelId` またはハンドルで照合し、既存タグを自動入力（未編集のとき）。`POST addChannel` |
| 送信項目（`addChannel`） | `token`、`channelId`、`handle`、`tags`（カンマ区切り） |
| 通信 | `POST`、`Content-Type: text/plain;charset=utf-8`、`credentials: 'omit'`。タグ取得は `?mode=tags&t=<時刻>` |
| キャッシュ | `addChannel` が成功したら `BM_TAGS` を破棄。タグを取得できないときは、手入力のタグだけで登録できる |
| 実装上の特徴 | `innerHTML` を使わず、`textContent` と DOM API のみで画面を構成。送信中はボタンを無効化して二重送信を防ぐ。`Esc` と背景クリックで閉じる |

## 6. 運用ルール

### 6-1. 設定値の同期

設定値は、複数のファイルに重複して定義されています。変更したときは、次の表のとおり、すべての箇所を更新してください。

| 変更内容 | 更新する箇所 |
| :--- | :--- |
| GAS の URL を再発行した | `config.js` の `GAS_URL`、`index.html`・`oshisuke.html`・`oshimado.html` のフォールバック値、`ブックマークレット.txt` の `CFG.GAS_URL` |
| 秘密トークンを再発行した（`rotateAdminToken`） | `ブックマークレット.txt` の `CFG.TOKEN`（再登録したブックマークも更新） |
| キャッシュキーを変更した | `config.js` の `CACHE_KEYS`、3画面のフォールバック値。BM タグのキーは `ブックマークレット.txt` の `CFG.BM_CACHE_KEY` |
| GitHub Pages の URL が変わった | 拡張機能の4か所（`manifest.json` の `matches`、`background.js` の `OSHIMADO_ORIGIN` と `OSHIMADO_PAGE_PREFIX`、`content.js` の `OSHIMADO_ORIGIN`）。拡張機能を再読み込みする |
| タグの折りたたみ閾値を変えた | `oshisuke.html` の `computeLocalFolded` と、GAS の `TAG_AUTO_VISIBLE_MIN_COUNT`（ブックマークレットの表示に使われる） |

### 6-2. キャッシュのオリジン分離

`LIVES` と `FULL` は、GitHub Pages のオリジンの `localStorage` に保存されます。`BM_TAGS` は、ブックマークレットを実行した `www.youtube.com` のオリジンの `localStorage` に保存されます。両者は別のストレージで、互いに見えません。

### 6-3. 拡張機能の更新

拡張機能のファイルを書き換えたら、`chrome://extensions` で再読み込みし、推しマド！のタブも再読み込みしてください。

## 7. 規模と性能の見立て・対策案

### 7-1. 規模の前提

| 項目 | 現在 | 想定 |
| :--- | :--- | :--- |
| 配信監視チャンネル | 22ch | 最大 40ch |
| チャンネルディレクトリ | 220ch | 約 300ch |

### 7-2. 実測値

**`updateLiveCache`（監視22ch、配信7〜8件）**

| 実行 | 処理時間 |
| :--- | :--- |
| 1回目 | 42.4秒 |
| 2回目 | 11.5秒 |
| 3回目 | 8.5秒 |
| 4回目 | 51.7秒 |

配信件数やキャッシュサイズはほぼ同じで、**データ量ではなく、API の応答速度が回ごとに約6倍ぶれています**（速い回は1チャンネルあたり約0.4秒、遅い回は約2.3秒）。ぶれに規則的な周期があるかどうかは、確認できていません。

**`updateChannelDirectory`（219ch）**：52.2秒（約0.24秒／ch）。GAS の1回あたりの実行上限（6分）に対して余裕があります。

**キャッシュのサイズ**

- チャンネル側：219ch で 95,308 bytes（約435 bytes／ch）。チャンク#0 が 81,525 bytes、#1 が 13,783 bytes。
- 配信側の本体：配信7件で 9,701 bytes、8件で約10.2KB（1件あたり約0.5KB。残りはタグメタなどの約6KB）。

### 7-3. 見立て

前提：更新は15分おき（1日96回）。数値は概算です。

| 項目 | 現在（22ch / 220ch） | 想定（40ch / 300ch） | 評価 |
| :--- | :--- | :--- | :--- |
| `updateLiveCache` の時間 | 8〜56秒 | 速い回で約15〜25秒、遅い回で約90秒 | 6分の上限には届かない。15分間隔のため、実行が重なることも起きにくい |
| API クォータ（`updateLiveCache`） | 約27ユニット／回、約2,600／日 | 約50ユニット／回、約4,800／日 | 既定の 10,000／日の約半分 |
| `updateChannelDirectory` の時間 | 52秒 | 約70秒（通常の速度） | 通常は問題ない。ただし、遅い回の速度（約6倍）が重なると、300chで約6分に迫る可能性がある（推測） |
| ディレクトリの件数 | 220件 | 300件 | 上限500件に対して余裕がある。キャッシュは500件で約218KB（3分割） |
| 配信側のキャッシュ（100KB 上限） | 約10KB | 配信が増えるほど増加 | 1件約0.5KBとして、**約180〜190件**で超過する見込み。超過すると、キャッシュを全削除し、毎回スプレッドシートから読む遅い状態になる |

### 7-4. 対策案（優先度順）

1. **計測の追加**（最優先・低コスト）：`updateLiveCache` の区間別の所要時間（プレイリスト取得・動画詳細取得・シート書き込み・キャッシュ保存）と、監視チャンネル数・動画 ID 数をログに出力する。遅い回の原因の切り分けに使う。
2. **並列取得への移行**（40ch 以上、または遅い回が常態化した場合）：`UrlFetchApp.fetchAll` で YouTube Data API を並列に呼ぶ。OAuth トークンの付与とスコープの確認が必要。更新時間を数秒〜十数秒に短縮できる見込み。
3. **ディレクトリ更新の分割・頻度調整**：300ch で遅い回が重なる場合に備えて、実行を分割する（件数を半分ずつにする、最新動画の取得頻度を下げる、など）。
4. **配信側キャッシュの保護**：保存する項目を絞る、または配信側も分割して保存する。件数やバイト数が閾値（例：80KB）に達したら、ログで警告する。
5. **設定値の一元化**：GAS の URL・キャッシュキー・タグの折りたたみ閾値が、`config.js`・各画面のフォールバック・ブックマークレット・GAS に分散している。`config.js` への集約を検討する（更新手順は 6-1）。
